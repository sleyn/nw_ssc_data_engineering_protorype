## 1. Understanding of the dataset

**Structure**: 11 CSVs, ~4MB, keyed by a patient/subject identifier that appears under 4 different column names across files (`case_number`, `reg_id`, `study_code`, `case number`) — normalized to one canonical `subject_id` at ingestion.

**The Registry**: `demographics.csv` and `ssc_subtype.csv` form a 1:1, 1,500-row master list — every row is `study=SSC-REG`, `diagnosis=SSc`. Every other table is a partial-coverage table of clinical/molecular events for a subset of these 1,500 patients (coverage ranges from 150 patients with a skin biopsy to 1,503 with any vitals record).

**A hidden second cohort**: 4 subject IDs (`SSC_NORM_0101/0102/0104/0110`) appear in `libraries.csv` (all 4), and partially in `mrss`/`pft`/`vitals` (3 of 4 — the 4th's RNA-seq sample failed QC and has no other records) — but never in the Registry. `libraries.csv`'s own comments confirm these are "healthy control sample[s]" used as a comparator arm for the RNA-seq work. Modeled explicitly as a `Subject` supertype with a `Cohort` attribute (`ssc_patient` vs `control`), rather than treated as orphaned/invalid IDs — a real structural finding, not a data error. The QC module's key-linkage check (ticket 03) automates this: it confirms all 4 against the known set and would flag any *future* out-of-Registry subject_id that doesn't match them as genuinely unexplained — currently 0 such IDs.

**Longitudinal vs. static**: `lab_report`, `vitals`, and `mrss` are long-format (component/category name + value, per patient per date) — internally unified as one "Observation" abstraction in code to avoid tripling near-identical logic, while staying distinct terms (Lab Result / Vital Sign / MRSS) in any user-facing view. `bal`, `medications`, `skin_biopsies` are event-based, not fixed-schedule. `demographics`/`ssc_subtype` are static, one row per patient.

**A naming trap**: `ssc_subtype.other_dx` looks like a differential/alternate diagnosis field but is actually semicolon-separated comorbidity flags (ILD, GERD, PAH, or combinations) layered on top of the uniform SSc diagnosis — every Registry patient's `diagnosis` is SSc regardless of `other_dx` content.

## 3. Data-quality issues and analytical findings

Each finding below states what was found, how it was verified, and what was done about it. All of these are now encoded as automated, advisory checks in `data/qc.py` (ticket 03) — the full generated report is `docs/qc_report.md`.

- **Height recorded in mixed units.** 1,235 of 1,500 patients have height in inches (54.7–78.5); the other 265 are in centimeters (141.3–194.7 cm ≈ 55.6–76.5 in) — a clean bimodal split at a threshold of 100, no ambiguous middle ground. Fixed at ingestion: cm-scale values converted to inches; raw CSV left untouched.
- **One high-confidence data-entry error, corroborated across independent records.** `demographics.csv` lists `subject_8545`'s weight as 22.5 (impossible for a living adult), but 5 separate `vitals.csv` visits spanning 2017–2020 all report ~160.6 lbs for the same patient. Decision: flagged in the QC report, not silently corrected — the vitals-based value is well-evidenced but `demographics.weight` is a distinct static field with no documented derivation from vitals, so overwriting it would assert a number we don't actually have provenance for.
- **A synthetic-data placeholder artifact, not a real clinical signal.** `WEIGHT IN POUND = 160.6` appears 870 times across 195 distinct patients in `vitals.csv` — the next most common weight value appears only 39 times. Some patients show this exact value on every visit across multiple years, which real weight measurements don't do. This is the same constant seen in the Control Subjects' vitals. First QC check added, `check_constant_value_across_visits`: flags a value that dominates far more *patients* than expected if personal-constant values (a value that never varies across a given patient's own visits, common and unremarkable on its own for low-cardinality vitals like blood pressure/pulse) were spread evenly across the distinct values observed for that measure. 160.6 scores ~106x that expectation; the next-highest anywhere in vitals (BP diastolic=77) scores only ~16-22x — nowhere close, so on this metric alone BP/pulse look clean.
- **The same pattern shows up in BP and pulse too, once measured the right way.** The per-patient check above is blind to a *record*-level filler used on only some of a patient's visits (a patient whose other visits genuinely differ won't clear the "never varies" bar, so those records never enter the per-patient dominance calculation at all). Looking instead at each value's share of *every* record for its measure: `BP SYSTOLIC=124` is 25% of all 7,848 systolic readings, `BP DIASTOLIC=77` is 25% of all 7,848 diastolic readings, `PULSE=76` is 16% of all 8,381 pulse readings — each several times the local rate set by its nearest neighboring values (11.7x / 5.7x / 4.6x respectively), a needle sitting on an otherwise ordinary distribution rather than a natural bell-curve mode. Second QC check added, `check_value_spike`, to catch this population-level-share pattern generically (also re-confirms 160.6 at 96.7x local background). Decision: reported as advisory QC findings alongside 160.6, not corrected or dropped.
- **PFT values are suspiciously, uniformly bounded.** `FVC`, `FEV1`, and `DLCO_SB` — three physiologically unrelated measures — all range exactly 40.0–130.0% predicted. Real measurements wouldn't naturally share identical bounds across different tests; this looks like generator clipping rather than organic data. Net effect: a clinical-guideline range check finds no outliers here, and that clean result is reported as a finding in its own right rather than treated as "nothing to see."
- **The same generic range check, run against `lab_report.csv` for the first time, surfaces injected errors nobody was looking for.** 9 of 19 numeric lab components each carry exactly 1-2 isolated, physiologically-impossible values: `ABSOLUTE LYMPHOCYTES`, `MCH`, and `MCHC` each have one `9999` sentinel; `WBC` has two `999` sentinels; `HEMOGLOBIN`, `NEUTROPHILS`, `LYMPHOCYTES`, `MCV`, and `NM BKR ABSOLUTE NEUTROPHIL` each have 1-2 negative values (impossible for any of those measures). A good talking point for why a *generic* check earns its keep: it wasn't built to find these specifically, it found them because it was pointed at a table nobody had manually audited yet.
- **Medication names fragmented across brand/generic/abbreviation.** Only 17 distinct medication strings total, but 3 of them — `CellCept` (192), `mycophenolate mofetil` (211), `MMF` (189) — are the same drug under three names. Unmerged, none individually ranks as the top medication; merged, the total (592) is nearly 2.5× the next most-prescribed drug (rituximab, 253) — this changes what "most-prescribed medication" looks like in any chart. Fixed at ingestion: canonicalized to one label, original preserved in an "as recorded" field.
- **Dose field is a small, mostly-clean lookup problem, not free text.** Only 24 distinct dose strings exist. Most are clean (`20 mg daily`, `500 mg BID`), but several look like intentionally injected errors: negative doses (`-1 tablet daily`, `-25 mg daily`), implausible magnitude/frequency (`999 tablets daily`, `10000 mg every hour`, `250 g twice daily` — likely a mg/g slip, ~1000× too high), and a unit-type mismatch (`500 mL tablets daily` — a volume unit on a solid dosage form). Built as a 24-row lookup table (dose string → value/unit/frequency), which both cleans up display and directly powers these implausibility flags.
- **Two distinct, non-overlapping missing-data gaps in medications**, not one: 20 rows have a dose but no medication name; 85 rows have a medication name but no dose. Confirmed no row has both fields blank.
- **PII-shaped fields exist despite the dataset being synthetic/non-PHI.** `demographics` has first/last name and birth date; `mrss`/`skin_biopsies` have `ENTRY_USER_NAME` (a clinician name, e.g. "Dr. Patel"). Decision: patient name/DOB suppressed everywhere downstream (subject_id + age-at-event only) as a deliberate demonstration of PHI-handling judgment; `ENTRY_USER_NAME` kept visible since it's provider-side operational metadata, not the kind of field HIPAA governs, and is useful for a "does score entry vary by rater?" angle.

## 4. Design decisions and tradeoffs

See `docs/adr/` for full write-ups; summarized here for the talk track:

- **HIPAA controls implemented literally, despite the data being confirmed synthetic/non-PHI and the deliverable requiring a public repo + public app link** (ADR 0001). Real login, real encryption at rest, real audit logging — gated by a published demo account, so the controls are genuine engineering rather than theater, without blocking reviewer access.
- **Encrypt the runtime data store, not the source CSVs** (ADR 0002) — keeps the repo clone-and-run reproducible (a reviewer can inspect the actual source data) while still having a real "encryption at rest" component to explain.
- **SQLite ingestion with a `Subject` supertype table**, not pandas end-to-end (ADR 0005) — chosen specifically because it models the Control Subject / Registry relationship correctly (cohort membership, not a foreign-key violation to explain away), and because the role's own scope ("data modeling... across clinical data sources") rewards showing schema design even at a data size where SQL isn't strictly necessary for performance.
- **Demo secrets file committed to the repo, against normal practice** (ADR 0004) — the credentials and encryption key are deliberately public by design (ADR 0001), so keeping them out of git would only add setup friction for reviewers with no actual security benefit; documented explicitly as a demo-only deviation.
- **Scope triage under a same-day deadline**: flat package layout over a layered architecture, minimal-but-real CI (ruff+mypy+pytest via GitHub Actions), targeted tests over exhaustive coverage, and the app's originally-planned 5th "discovery" page merged into the group-comparison page once it became clear they were the same free-form explorer.
